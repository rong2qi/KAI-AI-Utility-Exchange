## 代码接缝

新增 `dahono-router` Provider adapter，构造器注入 endpoint allowlist、key resolver、fetch、timeout 和 network mode。默认仍是 network-disabled；测试必须覆盖：payload 映射、SSE parser、usage、诊断头、401/403/429/5xx、超时、畸形响应和 key 不泄露。

### 写入 staging 测试密钥

密钥由操作者在本机隐藏输入，脚本通过标准输入交给 GitHub CLI，写入仓库 `staging` Environment 的 `DAHONO_API_KEY`。脚本只核对密钥名称和更新时间，不读取或打印密钥值：

```sh
npm run dahono:staging:secret
```

脚本不会写服务器 Secret Store，也不会自动预约或发起模型请求；服务器侧接入必须在真实 Dahono adapter 和 staging 运行时都准备好后，按同一密钥来源单独配置。若 GitHub 环境密钥写入失败，脚本退出并明确报告失败。

密钥和有效预约窗口都准备好后，才由受保护入口执行单次 live smoke：

```sh
npm run dahono:live:smoke -- --confirm-live
```

未显式带 `--confirm-live` 时不会读取密钥或出网，并以 `blocked` 证据结束。live smoke 只保存请求次数、Provider 请求 ID 哈希、用量、诊断头和输出长度；它不保存密钥或模型正文，也不替代并发、限流、事务存储和回滚验证。

如果密钥已经写入 GitHub `staging` Environment，使用仓库中的 **KAI Dahono live smoke** 手动工作流即可执行同一入口；工作流仍需要 `staging` 环境审批，且不会随 push 自动运行。

Provider 没有被确认提供上游幂等语义，因此 evidence 记录 `upstreamIdempotency=unsupported`。现有 Usage Execution Ledger 只避免重复已经记账的步骤；如果上游已执行而本地尚未保存，崩溃后仍存在再次付费调用的风险。接入真实业务前须增加“结果待确认”状态和对账路径，或验证供应商幂等/结果查询能力，不能以本地 request hash 宣称跨系统有效一次执行。

### 真实 10+1 与小样本计数验收

`npm run dahono:capacity:verify -- --confirm-live` 使用同一个 Dahono adapter，通过环境变量读取 `DAHONO_API_KEY`、`DAHONO_WINDOW_START`、`DAHONO_WINDOW_END` 和 `DAHONO_BOOKING_SLOT_ID`。预约 ID 由操作者或自动任务从已确认回执取得，经入口转换成 SHA-256 后进入验收器；用户无需手算哈希，证据不保存原始 ID。缺失或非法预约 ID 在读取密钥和出网前阻断。起止必须是带时区的 ISO 时间，间隔恰好一小时；启动时须位于窗口内并至少剩余五分钟。默认运行不取密钥、不出网。GitHub 的 **KAI Dahono capacity acceptance** 手动工作流提供同一入口，新增 `booking_slot_id` 输入，保存失败和未证明结果。

- 固定 HTTPS 目的地址，禁重定向；最多 14 次 POST、2 次 GET、总时长五分钟、单次推理三十秒，不自动重试。
- 前十个请求正常消费 SSE；只有十路都返回成功 SSE 响应头且尚未结束时才发第十一路。响应过快无法观察重叠时记录 `not_proven`，不延迟读取来伪造重叠。
- “十次调用成功”“绑定已确认预约”“发现接口身份一致”“十路未结束重叠”“第十一路 429”“429 可归因于并发”“小样本计数一致”由同一个纯评估函数分别判定。发现接口身份差异是独立诊断项，不能抹掉成功调用，也不会独自造成整体执行失败；已确认错预约、调用失败和过载检查明确不符则仍失败。缺失证据保留 `not_proven`，不会为获得绿灯降低完整容量标准。
- Dahono 同时声明 10 RPM 和 10 并发，429 时若 RPM 已耗尽，不能将它归因于并发；即使 RPM 尚有余量，当前诊断头也没有足以排除其他额度限制的原因字段。因此本版本保留限流原因的 `not_proven`，其他观察项可分别通过；未来取得可审查的供应商原因契约后再增强判断。这是本次证据的边界，不是 Provider 的执行禁令。
- `/models` 的计数只有与已确认预约同 slot 时才作为预约空闲/剩余额度门禁及计数基线。不同 slot 的遥测只记录身份差异，不替用户预约作决定。推理响应的预约身份独立于数值诊断头解析；任一响应明确属于其他预约时取消后续工作，即使其他头损坏也不能掩盖身份错误。只有十条流均未结束、身份正确且诊断有效时才发过载探测。取消不意味着上游请求未执行或未计费。
- 前十次调用成功、身份绑定正确且有同预约计数基线，即可进行三次间隔至少 65 秒的小样本调用，无需先触发第十一路。没有过载请求时共 13 POST，有过载请求时最多 14 POST。每条记录保存独立 `phase`、`index`、SSE 判据和时间，不把采样误判为过载请求。没有有效基线时不花费额外调用进行无效对账。
- 比较前后计数、成功请求 usage 和 slot 身份；计数统计时点或单位不一致时保留未证明结论，不能推导 20M/4M 整小时吞吐。五分钟总截止仍会中止剩余样本，不延长预算；已完成事实保留。其他客户端同窗口调用会污染计数，应隔离测试流量。
- 证据仅包含白名单状态、用量、诊断数值、身份哈希和源码指纹；不包含密钥、模型正文或原始异常。保存于 `evidence/dahono-capacity/`，CI artifact 保留 30 天。

通用 `concurrency-quota-acceptance` 只判断 burst 请求结果和合法 usage，不依赖 adapter 私有的 `peakConcurrency`，也不替调用方宣称禁网。离线 runner 另外记录 sandbox 的实际峰值和清理状态；真实流重叠与限流归因由 Dahono 验收入口负责。

### 将真实 Provider 组合进 staging，并逐步证明生产边界

当前 staging HTTP 服务只有 `/healthz` 与 `/version`，制品没有打包 Runtime/Provider；其 systemd 出网限制也没有开放上游访问。以下为 Exchange 封装和后续真实接入的关联工作，先以 sandbox 验证业务入口，再逐步完成对应接入，不把健康检查成功当作业务成功：

1. 增加独立组合入口：受认证 HTTP → `HourKeyRuntime` → 注入的 `ProviderAdapterPort`。同一请求可在 sandbox 和 Dahono 间更换配置，供应商细节仍留在 adapter。
2. 接入账号/Grant/Holding 校验、请求大小/时间/并发/用量限制和取消；保留白名单限流、窗口、认证错误，防止所有错误被统一成可重试“不可用”。先用隔离测试账号，经受保护通道验收。
3. 将密钥注入服务器侧 resolver，不进入制品和日志；仅调整本项目服务的受控 HTTPS 出网，继续隔离共享主机上其他项目。GitHub Environment Secret 不会自动进入服务器服务。
4. 为业务账本、Holding 和 Receipt 接真实数据库，验证多进程唯一约束、原子领取、fencing、恢复与扣减。已有发布状态事务的证据不替代业务事务；处理上游成功但本地结果未落盘的“待确认”间隙。
5. 同步修改 bundle 清单、远端 broker 白名单和工作流；回读源码/制品/运行版本，并从真实 HTTP 入口取得 Provider 结果及 Receipt。存活探针、配置就绪和付费推理分开检查。
6. 在隔离 staging 实际演练 A→B→故障→A，检查在途请求、数据兼容和审计，再用测试账号、流量上限和可关闭入口逐步验证生产流量。

以上是可实施的待接入边界，不是固定的“不可执行”结论。每项以对应实测记录推进，用户确认后才记为 `ACCEPTED`。

### 已查明的定义及仍缺少的契约

### 原始实测提示的计数问题

回读 17 点原件，十条 chat 响应按 active=1 至 10 排序后，头里的累计输入为 18、36、…、180，输出均为 0；每条最终 usage 则为输入 2,031、输出 499。当前不能把响应头数值直接当作最终结算账本与 usage 比较。准入预估、异步结算、注入提示或统计范围不同都只是候选解释，本轮没有证据选定原因，也不据此判定供应商错账。原件 SHA-256 保持 `7b73255e52438d6d900496cc38954629e865ed8747529661c2eedd3a2ef20379`。

Overview 前端另消费 `/v1/telemetry/stats` 与 `/v1/telemetry/timeseries`，可选 15 分钟、1 小时或 24 小时，展示 RPM、并发、请求数、输入/输出/cache/reasoning token 等字段。公开前端消费字段不等于完整后端接口契约；未定义这些读数的 slot/组织/key 范围、快照时间、时区和结算最终性。本轮未直接调用它们，不能仅因网页有曲线就选作预约对账来源。

### 四项证明的决定性证据

按当前用户决定，下列真实试验在 Exchange 封装就绪后从产品入口开展，同时保留供应商层观察。分别核对 Exchange 自身限流与上游 429、网关在途请求与真实上游 SSE 重叠、Exchange 回执用量与供应商最终账本，不能用其中一层的通过替代另一层的证据。

| 待证明项 | 如何开展 | 通过条件与边界 |
| --- | --- | --- |
| 真实十路流重叠 | 同一预约、隔离其他客户端，使用确实需要持续输出的任务，同时发起十路并正常消费 SSE；记录发出、响应头、结束及取消时间。 | 十路有效响应存在共同未结束区间，且最终全部成功。不可暂停读取制造重叠；供应商头中的 active=10 仅作辅助。若需要调整输出量或超时，应先修改有界测试配置并离线验证。 |
| 第十一路 429 与原因 | 在十路实际未结束时探测第十一路，保存 HTTP 状态、白名单错误原因字段、Retry-After、当时预约身份及其他配额状态。 | “收到 429”与“由并发触发”分开。优先用供应商稳定原因码/审计关联记录排除其他限制；不能仅凭 HTTP 429 判并发通过。 |
| 小样本计数一致 | 在同一预约和统计窗口内取权威起始计数，执行固定少量请求，再按供应商定义的结算时点读取最终计数；隔离其他流量。 | 最终请求数和 token 增量与成功请求 usage 总和一致。现有入口为十次成功后再做三次、间隔至少 65 秒的样本；也可另建三次请求的独立计数切片，先离线验证后执行。不得拿其他 slot 的 `/models` 数值作基线。 |
| 整小时额度 | 先分别冻结“一小时持续可用”“达到约定 token 吞吐”“额度耗尽后正确保护”的目标，再为相应目标定义完整预约时段的负载、总调用量、成本与停止条件。 | 稀疏调用一小时只证明该采样下的持续可用；要证明 20M/4M 实际吞吐，须实际完成相应量并与最终账本核对。缩小额度的限流试验只证明对应配置的保护逻辑，不能替代正式额度吞吐。 |

10 RPM 与 10 并发同时存在时，短时间直接发 10+1 天然混入每分钟限流。除稳定原因码外，可由供应商提供与目标策略一致、RPM 有额外余量的受控测试配置，或让真实长请求跨过 60 秒释放 RPM 后探测；改变 RPM 配置后的结果须明确限定到该配置。后一个方案要求长请求和新的超时边界，现有单请求 30 秒入口不能直接执行。两者均需先形成可审查测试方案，不沿用已结束窗口的授权。

### 封装后相关真实验证前应取得的四组答案

1. **身份与范围**：`/models`、chat、事后对账三者如何绑定预约；计数按什么身份聚合、是否跨 key 共享、时区是什么。
2. **计数与结算**：八个头的采样时点、token 定义、最终计数读取方式/收敛延迟、失败与取消如何记账；提供对账接口的完整契约或等价脱敏账本导出。
3. **拒绝与排队**：并发、RPM、RPH、token 配额各自的稳定原因码、检查顺序、Retry-After 含义，以及超并发究竟立即拒绝还是排队。
4. **无混淆试验**：供应商支持的十路持续重叠与第十一路探测方式、允许的输出量/耗时，以及可复现验收脚本的版本或源码。

这些是供应商契约待补项，可在 Exchange 封装期间继续做不消耗推理额度的资料核查，不要求用户自行发明参数，也不要求先等齐答案才开发业务封装。计数规则明确后，为“预约范围内的权威计数读取”设计独立接缝，发现接口继续只承担其已定义功能；原因字段映射、回归与有界参数纳入封装后的真实验收准备。此次没有实施该新接缝或修改运行代码。新的付费窗口与负载上限仅在封装就绪并取得对应授权后执行。

本计划完成后可以证明该 Provider adapter 和一次预约窗口内的真实模型调用。它仍不证明生产业务流量安全、数据库事务隔离、有效一次性执行，或坏制品触发的真实远端自动回滚；这些要按现有 staging 证据链分别验证。
